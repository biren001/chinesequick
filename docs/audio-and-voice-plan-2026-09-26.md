# 发音方案与竞品技术拆解（2026-09-26）

> 结论先行：**真人发音可以，但没有任何开源语料能给你——必须自己录。** 我已实测三个候选源，
> 数据在下文；同时发现现有的发音按钮在大量设备上是**静默失效**的，这个问题比"死板"更严重。

配套试听页：`_dev/audio-samples/samples.html`（自包含，含 5 个音色 × 3 句 + 慢速版 + 词级拼接对照）

## 一、先说一个比"死板"更严重的问题：现在的发音按钮在多数设备上是哑的

`components/AudioButton.tsx` 的逻辑：

```ts
const [supported, setSupported] = useState(false);
useEffect(() => {
  setSupported(typeof window !== "undefined" && "speechSynthesis" in window);
}, []);
```

`"speechSynthesis" in window` **只表示浏览器有这套 API，不表示设备装了中文语音**。
只要 API 在，按钮就是可点的、看起来一切正常，点下去**什么都不发生**。

实测证据（搜到的多份开发者报告一致）：

| 平台 | 中文语音现状 |
|---|---|
| Chrome / Windows | 需用户自己在「时间和语言 → 语音」里装中文语音包，**默认常没有** |
| Chrome / Linux | 默认无中文语音，需装 `speech-dispatcher-zh` |
| Safari / macOS | **不列任何 zh-CN 语音**，需手动启用"增强语音" |
| iOS Safari | 首次交互前 `getVoices()` 返回空，且常缺 zh-CN |

也就是说：**一个英语母语用户用没装中文语言包的 Windows，或直接用 iPhone 打开你的站，
点喇叭 = 没反应、也不报错。** 这是最糟的一类 bug —— 用户不会告诉你，只会觉得"这站是半成品"。

另外合成音还有硬性语言错误（多位开发者实测）：`重` 读 zhòng 不读 chóng、`一` 不做变调（一会儿→yí huìr）、
句末语气词一律拖平。这不是"死板"的审美问题，是**教错**。

**结论：音频必须变成我们自己的文件，无论走真人还是合成。**
附带好处 —— 文件在 `public/audio/`，`sw.js` 现在对同源 GET 就是 cache-first 按需缓存，
所以 **service worker 一行都不用改**，听过一次就离线可用。

## 二、三个开源音频源，我逐个实测了覆盖率

### ① Tatoeba —— 5,826 条普通话**句子**带真人录音（CC BY 2.0 FR）

这是理论上最诱人的一个：**句子级**、真人、许可证只要署名（无 share-alike）。
我把全量 5,826 条拉下来逐条比对你的 50 句：

| 比对方式 | 结果 |
|---|---|
| 逐字完全一致 | **1 / 50（2%）** —— 只有「没关系。」命中 |
| 宽松包含匹配 | 10 / 50，且**多数是错句**：`不要辣。`→`不要吵。`、`请给我水。`→`请给我一杯茶。`、`我不懂。`→`我不老。` |

**原因**：Tatoeba 的音频句子是随机的日常口语，不是为了旅行场景收录的。
这条路对"我指定的 200 句"基本无效。

### ② audio-cmn —— 8,596 条**词/字** + 1,707 条音节（CC BY-SA 3.0）

就是 Zitou 用的那套（Yue Tan 录 HSK 词表、Chen Wang 录音节）。
我读了仓库全量文件清单（39,599 个条目）来比对你的词汇表：

| 项目 | 实测 |
|---|---|
| 文件总数 | `18k-abr/hsk/` **8,596** 条、`18k-abr/syllabs/` **1,707** 条（另有 24k/64k/96k 四档码率） |
| 命名方式 | `cmn-多少.mp3`、`cmn-钱.mp3` —— **按词/字命名，全都是单个词，没有一条句子** |
| 覆盖你的 88 个词 | **68 / 88（77%）** |
| 缺的 20 个词 | 打包 买单 火车站 哪儿 空房 入住 退房 Wi-Fi 寄存 早餐 刷卡 袋子 …… |

**注意缺的这批词** —— 全是旅行场景专属词（入住/退房/空房/寄存/打包/买单）。
这正是你这种"旅行者向"产品的核心词汇，而语料恰恰在这里是空的。

而且即便词全有，也**拼不出句子**：试听页里我给你放了一条用 `多少 + 钱` 直接拼接的对照音频，
词与词之间的停顿和语调衔接是断的（拼接脚本见 `_dev/make-tts-samples.py`，素材经 jsDelivr 拉取）。

> 顺带一个可写进营销的判断：**Zitou 的 about 页把"8,500 条母语者录音"当卖点，但那全是词级。**
> 它的句子朗读只能靠合成或干脆没有。**我们只要录出 200 条整句真人音，就在它最得意的那个指标上超过它。**

### ③ Mozilla Common Voice 中文 —— 21.4 GB，CC0 —— **但不能用**

| 项 | 值 |
|---|---|
| 规模 | `cv-corpus-27.0`（2026-09-17 发布）中文（中国大陆）**21.40 GB**，另有 zh-HK 3.43 GB / zh-TW 2.96 GB |
| 许可证 | CC0-1.0（署名都不要） |
| **限制条款** | 官方明写：**禁止 re-host / re-share 本数据集**、禁止推断说话人身份；定位为 **ASR 训练与评估**用途 |

CC0 本身允许任意使用，但它附加的"禁止再分发"条款把我们"打包进静态站分发"这条基本盘掐死了。
它可以用来**训练模型**，但我们不做这件事。**排除。**

### 小结（这张表是本次最重要的结论）

| 源 | 是什么 | 能给你整句真人音吗 |
|---|---|---|
| Tatoeba (CC BY 2.0 FR) | 5,826 条句子录音 | ❌ 实测命中 2% |
| audio-cmn (CC BY-SA 3.0) | 8,596 词 + 1,707 音节 | ❌ 一条句子都没有 |
| Common Voice (CC0) | 21.4 GB 朗读句 | ❌ 条款禁止再分发 |
| **自己录** | 你要多少有多少 | ✅ **唯一可行** |

## 三、Zitou 的技术栈拆解：哪些能抄，哪些抄了也没用

你把它的许可证清单贴对了。逐条说这份清单对我们意味着什么：

| 它用的 | 许可证 | 我们能拿什么 |
|---|---|---|
| CC-CEDICT | CC BY-SA 4.0 | 可以拿，120 万词条汉英词典，**署名 + 同协议**。但这是它的护城河所在（7,823 个 `/w/<汉字>` 页），抄了就是跟它正面打，不划算 |
| audio-cmn | CC BY-SA 3.0 | 可以拿词级音频（见上，**句子拿不到**） |
| 汉字笔顺数据 | Arphic PL / LGPL | 可以拿。适合做"写字动画"，但你的用户是旅行者，**优先级低** |
| Hanzi Writer | MIT | 可以拿，MIT 最宽松。同上 |
| Tatoeba 例句 | CC BY 2.0 FR | 可以拿，但句子跟你的场景不匹配（实测 2%） |
| HSK 词汇表 | MIT | 可以拿。**但你明确不做 HSK**，拿了也没处用 |
| Nunito 字体 | SIL OFL 1.1 | 可以拿，商用免费 |

**关于作者**：Zitou 由 **Maqsudjon Polatov** 在**塔什干**（乌兹别克斯坦）创建，是 `tou.gg` 项目之一，
另有作业向应用 `zh.tou.gg`。名字取"字头"（zìtóu，汉字上部，如"草"字的"艹"）。
他在 about 页**明写接受合作**（Telegram `@toudotgg`），并且自述乌兹别克语/俄语释义是 AI 生成、正在校对、可能有错。

> **他真正的短板不是技术，是母语**：一个塔什干开发者做中文学习工具，释义靠 AI 翻、
> 音频靠开放语料拼。你在语言能力和场景理解上对他有结构性优势 ——
> **但这个优势只有在你自己出声（或找人出声）时才转化得出来。**

## 四、三条路线，我的推荐

| | A. 自己录真人 | B. 神经语音预生成 | C. 开源语料 | 
|---|---|---|---|
| 质量 | **最好**，真人语气 | 接近真人，偶有机器味 | 词级可用，句子不可用 |
| 工期 | 录入 138 条 ≈ **25–35 分钟**；200 句时 ≈ 1.5–2 小时 | **几乎为零**（脚本跑几十秒） | — |
| 成本 | 0（你出声）；外包约 $30–60 | 0 | 0 |
| 版权 | **完全自有**（也可选 CC BY 方便导流） | 需确认服务条款 | 需署名 / 部分同协议 |
| 离线 | ✅ | ✅ | ✅ |
| 差异化 | **可以直接写进卖点，压过 Zitou** | 无（谁都能做） | 无 |
| 风险 | 需要安静环境、一次性录完保证音色一致；若口音不标准会暴露 | 听众仍可能听出合成 | 见第二节，**不成立** |

**我的推荐：A 为主，B 兜底。**

具体地：

1. **现在用 B 把音频补齐**（我可以今天做完）：把 50 句 + 88 词全部用 `zh-CN-XiaoxiaoNeural`
   预生成为静态 mp3 落进 `public/audio/`。**这一步的主要目的不是终态，而是立刻修掉那个静默失效的 bug** ——
   装上文件后，任何设备、离线、都不再依赖系统有没有中文语音。
2. **然后你按自己的节奏录 A**，录好一条替换一条（编号一一对应，替换是原子操作，不用改代码）。
   全替换完，我们把 about 页的"发音怎么来的"改写成"真人录制"，并加一句
   *"Every phrase on this site is recorded by a native speaker — no text-to-speech."* —— 这是竞品抄不走的句子。
3. **不要走 C。**

**A 的配套我会做**（等你确认后动手）：

- `_dev/record.html` + 一个本地小服务：屏幕上一次显示一句（大字 + 拼音 + 英文），
  按录音→停→回放→满意就存盘。存成一个 wav 落进 `recordings/`，**支持中断续录**（已录的自动跳过）。
  200 句也可以分几次录完，不用担心一次做完。
- `_dev/build-audio.py`：读 wav → ffmpeg 去首尾静音 + 响度统一（EBU R128，`loudnorm`）
  → 编码 64 kbps 单声道 mp3 落进 `public/audio/{id}.mp3`。
  **本机已确认有 ffmpeg**（`/c/ffmpeg-.../bin/ffmpeg`），全离线、不需要装任何东西。
- 代码侧：`Phrase.audio` 从 `null` 改成路径；`AudioButton` 改成优先播放文件、
  文件不存在才退回合成（并**把 `supported` 判断改成"真的存在中文语音"**，修掉第一节那个 bug）。
  体积估算：138 条 ≈ 2.6 MB；扩到 200 句 + 250 词 ≈ 8.5 MB，都是按需缓存，首屏不受影响。

**唯一的诚实提醒**：录制音色必须一致 —— 同一支麦、同一个房间、同一次坐下来录完。
东一句西一句拼起来的音频听起来会比干净的合成音**更差**。如果做不到一次性录完，宁可用 B。

## 五、关于"用圣经学中文"那位

先纠正一个常见的许可证误会：

| 资源 | 文本 | 音频 |
|---|---|---|
| 和合本 CUV（1919） | **公有领域**，随便用 | ❌ 各家的朗读音频都有版权，Bible.is / 环球圣经公会**不允许再分发** |
| YouVersion (bible.com) | 可免费阅读 | 仅供站内收听 |
| **unfoldingWord Open Bible Stories** | ✅ **CC BY-SA 4.0** | ✅ **有音频，同一许可证** |

**唯一干净可用的组合是 unfoldingWord Open Bible Stories**（CC BY-SA 4.0）：50 个圣经故事，
有简体中文文本 + 音频 + 插图，在 `door43.org` / `openbiblestories.org`。
用法是署名 + 衍生作品同协议；注意它的商标不能出现在修改过的衍生作品上。

**但我建议现在不要做这件事**，理由三条：

1. **它会变成一个新的内容垂直领域**。你一旦托管经文，就要承担译文维护、注释、教义中立性
   （你面对的是全球用户）等一整套负担 —— 而这不是你的产品方向。
2. **CC BY-SA 会粘在那些页面上**。你精心设计的整站版权一致性会被打开一个口子。
3. **搜索需求本来就不在 Google 上**。那位提问者是"想学中文 + 想学圣经"，
   他真正的入口是海外华人教会和差传社群。这条路对 SEO 几乎没有回报。

**低成本替代（如果只是想让那位朋友有个去处）**：

- 直接把他导向 **Open Bible Stories** + YouVersion 的**中英对照**阅读 + Pleco 查词 —— 免费、合法、立刻可用，上一轮我已经给过。
- 在你站内，值得做的**只有一篇指南**：*Learn Chinese by reading texts you already know* ——
  讲方法（用已知内容换"可理解输入"），落点在**你自己的双语对话**上，不托管任何第三方经文。
  这样既接住了这类长尾搜索，又不碰版权和垂直领域。这篇可以并进 P1 的指南清单。
